# NexFEM team conventions

Shared rules for every model working on NexFEM (Claude, Codex, ChatGPT) and for the owner. `CLAUDE.md`, `AGENTS.md` and `docs/CHATGPT_KICKOFF.md` point here. If another document conflicts with this file, this file wins. Raise the conflict with the owner instead of choosing silently.

## 1. End-of-turn report line

Every turn ends with exactly one line in this form, including turns that only answer a question:

```text
[UTC yyyy-mm-dd hh:mm] Đã làm: <what was done> | Việc kế tiếp: <one concrete next task> | Ai làm: <Owner | Claude Opus/Sonnet/Haiku | Codex | ChatGPT>
```

- Use UTC and the time the turn ends.
- **Ai làm** names one assignee and a model tier from section 6. Use `Owner` for decisions, merges and Windows acceptance testing.
- If the turn changed a task, write the same next task and assignee into the task file's `next` and `assign` fields (section 2).

## 2. Source of truth for status

- **GitHub issues and PRs are the source of truth:** state, review, CI and merge status. Check them before trusting any file.
- **Each task has one file:** `docs/checkpoints/<id>.md`, where `<id>` is the branch name with `/` replaced by `-`. Only the task's owner edits that file. Rules and header fields are in [docs/checkpoints/README.md](checkpoints/README.md).
- `PROJECT_STATUS.md` is generated by `python3 scripts/checkpoint_index.py`. Never edit it by hand. It lists each pending task's next step and assignee.
- To see which session was active last on any branch, run `python3 scripts/checkpoint_index.py --latest`.
- Commits made by a model end with these trailers:
  - `Agent: <name> (<model>)`
  - `Agent-Session: <link or ID>`

  Claude's `Claude-Session:` trailer also counts.

## 3. Merging

- Merge a PR only when the owner explicitly says to merge **that** PR. Approval of a plan, a passing CI run, or a review comment is not permission to merge.
- Do not delete a task file before its PR is merged. When work finishes, set `status: DONE` instead. Deleting a task file is a separate step, done after the merge and only when the owner asks.
- Never force-push or rewrite history on a branch someone else owns.

## 4. Builds and releases — POLICY-001

- Models do not build the desktop app or its installers, and do not publish releases, tags or installer artifacts.
- The repository's existing CI pipeline (automatic builds, installer tests, preview releases) is not affected by this rule.
- Allowed locally: type-checking, unit tests, the Rust tests and the benchmark scripts. If a check needs a full app build (for example, Playwright end-to-end tests), leave it to CI and say so in the report.
- Exceptions need the owner's explicit approval in the conversation, recorded in the task file.

## 5. Language

- Reply to the owner in Vietnamese.
- Write in English in the repository: code, comments, commit messages, PR text, task files and documentation.
- Existing Vietnamese documents stay as they are until they are next substantially edited.

## 6. Model guidance

| Work | Suggested model |
| --- | --- |
| Hard code: solver, schema, CSI import mapping, anything where a silent error produces wrong engineering results | Opus (or the strongest model of another vendor) |
| Small fixes, documentation, routine updates, code review | Sonnet (or a mid-tier model) |
| Look-ups: checking CI or PR state, finding a file, reading a value | Haiku (or the lightest model) |

- The reviewer of high-risk work must be a different model from its author.
- Detailed routing by code area is in `docs/WORK_ROUTING.md` on the application branch.

## 7. Limits of this file

- A model that cannot read the repository, such as a new ChatGPT conversation, does not see these rules. Paste [docs/CHATGPT_KICKOFF.md](CHATGPT_KICKOFF.md) at the start of each such conversation.
- These rules take effect only once they are merged into `main`.
